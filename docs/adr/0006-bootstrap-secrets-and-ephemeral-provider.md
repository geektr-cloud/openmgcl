# Bootstrap secrets 由独立 ephemeral provider 提供

mgcl 只接管首次运行 OpenTofu 前必须准备的 bootstrap credentials（IAM access key、跨云凭据等），不自动导入或接管 OpenTofu 创建的 state outputs。Secret 是 KV 集合；同一个 Secret 共用一把独立 Secret DEK，KV 分别加密，但绝不复用 State Lineage 的 Lineage Key。凭据与 state 复用同一 `mgcl.db`、同一 SSH Recipient/identity，使用独立 secrets 表、独立 envelope 标签/AAD 和密钥元数据；只保留最新 KV，不做历史版本、多 Recipient 或 DEK rotation。备份 `mgcl.db` 与私钥即可恢复；私钥丢失不可恢复。

唯一主接口是 OpenTofu >=1.11 的 ephemeral resource，首版只支持 `mgcl run -- <command>` 的子进程；常驻 `mgcl run` 不签发 provider session token，也不增加获取常驻 provider token 的能力。用户 TACOS Bearer token 与 provider session 独立：未显式配置时每次 run 自动生成，子进程模式只写入临时 CLI config 且不打印，常驻模式在监听后打印一次；显式 token 保持固定值且不打印。`mgcl run` 为每次启动的子进程生成密码学随机、短期、限定路径的 provider session token，通过 `MGCL_PROVIDER_ENDPOINT` 和 `MGCL_PROVIDER_TOKEN` 注入；provider session 注入的只有 endpoint 与 token，Secret value 不进入环境，而由 provider 通过 API/RPC 读取后留在 tofu/provider 内存。token 只能调用固定的 Secret read/write/delete/write-batch 路径，不能读写 TACOS state，也不能执行管理操作；它与用户 token、SSH passphrase 不复用。provider 位于独立仓库 `github.com/geektr-cloud/terraform-provider-mgcl`，本仓不内嵌 provider，也不采用 monorepo 或本地 registry 模拟；本仓未来提供 stdlib-only 的 `pkg/providerapi` 供其导入。开发期用 `go install` 生成 provider 二进制，`dev_overrides` 快速验证，filesystem mirror 覆盖需要 `tofu init` 的路径；正式无缝 `tofu init` 等 GitHub Release 与 OpenTofu Registry 发布后再提供。

非 loopback 监听默认需要二次确认。`mgcl run` 同时检查有效 listen host 和有效 serverURL；只有两者 host 都是字面 `127.0.0.1` 才免确认，`localhost`、`::1`、`0.0.0.0` 等都要在加载私钥/DB 和监听前确认。TTY 提示会公开 state 与 secrets，非 TTY 必须显式使用 `--yes-i-know-it-will-publish-state-and-secrets`。`--server` 只是 TACOS 对外 URL，不用于 provider endpoint；Secret API 仍要求有效 provider token，安全门放宽的是网络暴露面、token 和 HTTP 明文流量风险，不是认证。这是允许用户承担风险的逃生门，最终不采用“secret API 永远只限 loopback”的方案。

访问可见性属于每个 KV：`secret_kvs.is_ephemeral` 默认为 1，新建 KV 都是 ephemeral；`mgcl secret set --public` 在写 KV 的同一事务中只把该 KV 置为 `is_ephemeral = 0`，不影响同一 Secret 的其他 KV。`POST /api/mgcl/v1/secrets:read` 的 `access: "ephemeral"`（含空值）返回该 Secret 全部 KV 及其 `is_ephemeral` marks，因为 `mgcl_secret` 必须得到完整 KV 集合；`access: "public"` 只选择并解密 `is_ephemeral = 0` 的 KV，没有匹配时返回空 map，不做 Secret 级 403。分离的原因是 ephemeral resource 的值不会进入 plan/state，而 public provider function 的返回值可能进入 plan/state 和日志；由用户对每个 KV 显式选择哪种消费方式。public 不是明文：KV 仍 AES-256-GCM 加密，仍需要私钥，`--public` 只是访问标记。`access` 不是 token 级能力划分：同一 provider token 可以声明任一 access，服务端只按 KV 标记过滤，无法识别调用来自 ephemeral resource 还是 public function；隔离依赖 provider 各调用点使用正确 client 方法。public 读取不暴露非 public KV 的名称或密文，404 只表示 Secret 不存在，这是同一数据库信任域内接受的信息面。managed resource 需要写路径，因此 provider session 还可调用 `secret-kvs:write` 与 `secret-kvs:delete`：write 在同一个 `BEGIN IMMEDIATE` 事务中按需创建 Secret、独立 DEK 和目标 KV，delete 幂等且保留空 Secret。DB 不做自动迁移或版本管理；v0.1.0 旧库由外部一次性程序加字段，在 `/tmp/mgcl-migrate` 目录构建后运行 `/tmp/mgcl-migrate/mgcl-migrate ./path/to/my.db`（或进入该目录运行 `./mgcl-migrate ./path/to/my.db`），迁移工具删除 `secrets.is_ephemeral`（若存在）并添加 `secret_kvs.is_ephemeral`，旧列值忽略。

Secret name 采用层级形式：一个或多个 `/` segment，每段匹配 `^[a-z0-9][a-z0-9_-]{0,63}$`，完整名称不超过 64 字节；KV key 仍是单段，完整 KV 引用与 function wildcard 都按最后一个 `/` 拆分。单段旧名称/引用继续兼容，不需要 schema migration。managed resource 需要一次原子更新多份 KV 时使用 `secret-kvs:write-batch`：batch 只拥有请求点名的 KV，未提及的 KV 保留；`ensure: true` 或非空 `kvs` 可在需要时创建 Secret，纯 delete 对缺失 Secret 幂等成功；delete 和 batch 都不删除 Secret。整批 upsert/delete 在一个 `BEGIN IMMEDIATE` 事务中按最终 KV 集合校验限额并原子提交，失败全部回滚；不承诺跨调用的顺序或幂等判断。

未采用把云凭据作为环境变量注入（会进入进程树、日志和子进程环境；短期 provider token 的 endpoint/token env 注入不在此列，它不承载云凭据）、provider function（返回值不能标 sensitive/ephemeral，可能落入 plan/state）、cloud workspace variables（本地 plan/apply 不读取）、普通 data source（值会进入 state）、复用 Lineage Key（把 bootstrap 凭据绑到 state lineage 生命周期，扩大影响面）、独立 `secrets.db`（破坏“db + 私钥”单份备份恢复）、内嵌 provider/monorepo/本地 registry 模拟（耦合发布与安装），以及自动导入 state outputs（超出 bootstrap 边界且与既有 state 加密重复）。

后果：首版没有 CI/无人值守、多 Recipient、撤销、DEK rotation、secret 历史、安全擦除，也不发布 provider 到 Registry；endpoint/token 会继承给子进程树，不构成同用户进程隔离。完整契约见 [secret-management.md](../secret-management.md)。
