# SQLite 备份目标采用 sqlite: 与 path: 两种不可互换语义

mgcl 的恢复单位仍是“一份 `mgcl.db` + 一把 SSH 私钥”。备份目标只是这份数据库的可选覆盖副本，不引入版本历史、恢复 API 或新的密钥体系。目标环境分成两类：正常本地文件系统可以使用 SQLite 锁和 Online Backup API；某些挂载不支持 SQLite 锁，只能做普通文件 I/O。用一种机制同时覆盖两者，要么在无锁挂载上直接失败，要么在运行中热拷贝一个可能依赖 WAL 的文件。因此首版固定两种 scheme：`sqlite:<path>` 与 `path:<path>`。

`sqlite:<path>` 使用 modernc SQLite Online Backup API。启动、接受写流量之前先做一次全量备份；之后每个成功写提交只标记 dirty，由单一后台 worker 合并同步所有 sqlite 目标。每轮为每个目标新建 backup handle，`Step(-1)` 直到 DONE 后 `Finish`；没有固定周期，空闲不复制。写请求在源事务提交后即可返回，允许目标暂时落后；关闭前必须 drain 最后一轮。目标是被覆盖的 SQLite 数据库，要求目标文件系统支持 SQLite 锁。同步失败时记录首个致命错误、停止接受新写并终止当前写会话；已提交的源事务不能回滚。

`path:<path>` 为不支持 SQLite 锁的挂载准备，使用最纯粹的文件 copy，不使用 `VACUUM INTO`。启动时只在目标同目录创建一个 0600 的临时 RW 探测文件，写、关闭、删除，任何一步失败都不启动，且不碰正式目标。运行中不同步；停止写流量、drain sqlite worker、主 WAL checkpoint 成功并关闭主会话之后，才验证主文件自包含，复制到目标同目录的唯一临时文件，fsync 后 rename 原子覆盖目标。目标始终是单一自包含文件，不依赖 sidecar。

两种语义不能互换：`sqlite:` 在运行中更新，失败在运行中暴露；`path:` 只在干净关停时更新，失败在关停时暴露，目标在两次干净关停之间保持旧内容。切换 scheme 会改变新鲜度、失败时机和关停时长，属于用户可见合同，不能静默迁移。两者都覆盖最新副本，不做版本轮换；`sqlite:` 原地覆盖还可能让失败后的目标不再代表上一份成功副本，`path:` 则用临时文件加 rename 保留旧目标直到新副本完整。

整体采用 fail-closed。启动校验、path 探测或 sqlite 初始备份失败则不启动；运行中任一 sqlite 同步失败则记录首个错误、停止接受新写、终止当前 run/写命令，并尽量完成和报告其他目标，最终以 1 退出。终止子进程可能中断正在执行的 `tofu apply`；这是为了避免继续产生无法备份的写入。path 在关停时失败同样令命令失败，不跳过。备份失败不能撤销已经提交的源事务，源数据库仍可能领先于目标；实现不得把这种情况包装成成功或静默 best-effort。

未采用每次写返回前同步备份（把备份延迟压到写路径，且无版本化时并不能提供更强恢复保证）、固定周期快照（空闲时无意义复制，周期也无法表达写后立即同步）、运行中复制主文件（WAL 下不是自包含快照）、`VACUUM INTO`（仍依赖 SQLite 锁，且不是纯文件 copy）、版本轮换/保留策略（扩大首版范围）、以及 `MGCL_BACKUP_TO` 环境变量（备份是显式、可审计的每命令决定，避免隐藏目标）。

后果：sqlite 目标在两次成功同步之间可能落后；进程被 SIGKILL 或断电时无法 drain，目标可能停留在上一轮。path 目标要求干净关停，且 checkpoint 会被其他活跃连接或非空 WAL 阻塞。symlink/hardlink 检查只做尽力检测，不是同用户攻击者的安全边界；备份内容沿用已加密数据库，不额外解密，也不承诺安全擦除。完整实现与验收合同见 [database-backup.md](../database-backup.md)。
